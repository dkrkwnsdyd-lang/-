# SHOP SHORTS AI — AI 개발팀 운영 규칙 (v1, 2026-10-24)

## 적용 범위와 목표
- 기존 Python/FastAPI/PWA/FFmpeg 저장소에 **개발 운영 체계**를 추가한다. 현재 영상 엔진을 다른 프레임워크로 다시 만들지 않는다.
- 기획 → 설계 → 구현 → 자동 검사 → 실사용 검증 → 승인 → 배포 → 운영의 단계를 한 변경 단위(PR)로 추적한다.
- 이 문서는 ChatGPT, Claude Code, Codex 간의 **공통 인수인계 계약**이다. 문서만으로 서로의 세션이 자동 연결되는 것은 아니다. 자동 오케스트레이션은 별도 API/권한/실행기를 갖춘 뒤 구축한다.

## AI 역할과 책임
| 역할 | 주책임 | 필수 산출물 | 할 수 없는 것 |
| --- | --- | --- | --- |
| ChatGPT (기획/PM/설계) | 요구사항, 우선순위, 구조/보안/비용 검토, 수용기준 | GitHub Issue 명세, 위험 목록, Acceptance Criteria | 실제 검증 없이 완료/운영 중이라고 선언하지 않음 |
| Claude Code (구현 리드) | 기존 아키텍처 읽기, 작은 단위 구현/리팩터링, 사용성 검토 | 변경 코드, 변경 이유, 테스트 명령/결과 | 대규모 재작성, 비밀키 공유, 임의 유료 API 호출 |
| Codex (독립 검증/버그수정) | 변경 범위 확인, 회귀/엣지 케이스, 작은 안전 수정 | 테스트, 재현 단계, 차이/위험 보고 | 구현자의 주장만으로 PASS 판정 |
| GitHub Actions (기계적 검사) | PR에서 오프라인 스모크 및 문법 검사 | 체크 결과와 로그 | 실영상 품질/상업적 성과를 보장하지 않음 |
| 사용자 (최종 승인) | 비용 발생, 외부 게시, 프로덕션 배포, 최종 영상 품질 판정 | 승인/보류 결정 | 승인 없이 유료 생성/게시되지 않음 |

> Claude/Codex는 연결된 실행 환경에서 각각 호출해야 한다. 현재 문서는 역할과 기록 형식을 통일한 첫 단계다.

## 표준 절차
1. **기획**: Issue에 문제/목표/비목표/수용 기준/데이터 출처/권리/비용/테스트 계획을 작성한다.
2. **설계**: 기존 `PROJECT_STATUS.md`, `NEXT_TASKS.md`, `API_STATUS.md`, `TEST_RESULTS.md`, 관련 코드를 읽고 기존 기능을 재사용한다. API/DB/UI 변경 범위와 롤백 경로를 적는다.
3. **개발**: Issue 하나당 작은 브랜치/PR 하나. 먼저 재현 또는 실패 테스트, 구현, 회귀 테스트를 진행한다.
4. **자동 검사**: PR에서는 비밀키/유료 호출 없이 `compileall` + pytest 스모크를 실행한다. 전체 테스트는 환경이 준비되면 수동으로 실행하고 증거를 기록한다.
5. **품질·보안 검수**: 상품 고정(Product Lock), 사실 근거(A/B/C), 광고/제휴 고지, 영상·이미지 저작권, 민감정보, 비용, 모바일 사용성을 확인한다.
6. **승인**: 사용자 승인 없이는 실제 SNS 발행, 비용 발생, 저장소 기본 브랜치 병합, 서버 배포를 하지 않는다.
7. **운영**: 실패 사유, 재현 자료, 롤백 절차를 남기고 `PROJECT_STATUS.md`/`NEXT_TASKS.md`/`TEST_RESULTS.md`를 실제 결과로 갱신한다.

## PR 병합 품질 게이트
- [ ] 요구사항/변경 범위/수용 기준이 PR에 존재
- [ ] 자동 테스트 PASS 또는 실패 원인과 보류 결정 기록
- [ ] 기존 `/classic`, `/control`, PWA 및 V2 경로 영향 분석
- [ ] 사실·상품 외형을 임의 생성하지 않음 (가격·할인·평점·판매량·경험 등의 허위 주장 방지)
- [ ] 외부 미디어 사용 권리와 제휴 고지 확인, 미확인은 `BLOCKED`로 기록
- [ ] 새로운 외부 API는 공식 사양·권한·단가 확인 전 비활성
- [ ] 비용 발생/영상 게시/실배포는 사용자 승인 후 진행
- [ ] 변경 전후 결과, 테스트 한계, 롤백 방법 기록

### 완료/미완료 표현
- `IMPLEMENTED`: 코드만 작성
- `TESTED_OFFLINE`: 격리된 테스트로 확인
- `TESTED_REAL`: 실제 입력 및 실제 결과를 확인
- `REVIEW_NEEDED`: 사람의 시청/업무 검토 필요
- `BLOCKED`: 권한·키·소스·조건 미충족
- `RELEASED`: 실제 배포/발행 성공 증거 존재
코드 존재 자체를 `RELEASED`로 보지 않는다.

## 현실적인 1차 백로그
1. **P0 전략 점수 무효화 결함**: Preview에서 대본/자막 변경 후 Conversion Audit 재계산되지 않는 문제. 변경 즉시 기존 점수를 `STALE` 처리하고 새 점수/게이트 확인 전 출력을 허용하지 않는 정책을 설계한다. 기준: 편집 전후 점수 차이, 게이트 실패 차단, 과거 작업과의 호환, 회귀 테스트.
2. **P0 실제 제품 품질 검증**: 사진 2장과 사용 영상 3~10초 입력 사례를 별도 시험하여 사람 검수와 Final QA를 비교한다. 합성 fixture 결과와 실측을 섞어 성공으로 표시하지 않는다.
3. **P1 전략 속도**: LLM 호출 수/시간/비용을 먼저 측정한 뒤 캐시·병렬화를 시험한다. 사실 검증과 Product Lock은 생략하지 않는다.
4. **P1 UX**: 모바일 PWA에서 Preview→수정→승인→MP4 흐름 실기기 검증.
5. **P1 소스 권리**: 쿠팡/판매자 이미지, 사용자 촬영, 무료 스톡을 구분하고 권리 확인 상태가 불명확하면 게시 보류.

## 테스트 및 배포 경계
- 로컬: `python -m pip install -r requirements.txt 'pytest>=8' 'httpx>=0.27'` → `python -m pytest -q`.
- CI: `.github/workflows/ai-team-checks.yml`. 스모크 통과와 전체 테스트 통과는 다르다.
- 생성 영상의 `COMPLETE`는 이 저장소의 품질/컴플라이언스 게이트 판정에 따르고, AI의 답변만으로 강제하지 않는다.
- 기본 브랜치와 프로덕션 인프라를 보호한다. 롤백은 기능 변경 전 커밋/백업 기준으로 정리한다.
- API 키와 인증 값은 `.env` 등 비추적 파일 또는 비밀 저장소에 둔다. `.env.example`에는 실키를 넣지 않는다.
